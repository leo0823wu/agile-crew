# 全面情境盤點清單

PM 拆需求、QA 寫測試案例時逐項過。不是每項都適用，但每項都要**有意識地判斷「不適用」**，而不是沒想到。

## 1. 人與角色
- [ ] 誰會碰到這個功能：前台訪客、登入會員、後台人員（不同權限）、客服、排程／自動流程、外部系統。
- [ ] 每個角色**看到什麼、能做什麼、做錯了怎麼辦**。
- [ ] 任何「需人工處理」：誰處理？在哪個畫面看到原因？按什麼完成？處理完系統怎麼恢復？（沒有畫面＝死路）
- [ ] 使用者被擋下時，畫面有沒有告訴他**原因與下一步**，而不是「處理中」「請聯絡客服」就結束。

## 2. 規則一致性（同一條規則的所有出現處）
- [ ] **講業務規則之前**（例：「一次扣多少」「多久算一次」）：照每一種類別（商品類型、方案、角色）各自用實際資料核對一次，不要拿其中一類的結果套全部；只從部分資料推出來的，回報時寫「推測」並請使用者確認。也要列出規則在程式裡的**每個檢查點**各自檢查什麼（例：送出時只看次數、排程只看餘額），不要只看計算公式（2026-11-10：把其中一類的扣抵規則講成全部適用，使用者追問才逐類核對，另一類其實長度不固定）。
- [ ] 需求寫「改成跟 X 一樣／一併更新 B、C」：判斷是**在各自原本的東西上做同一個修改**（預設）還是**整個換成 X**；整個換掉會動到需求沒提的內容，先附兩種做法的畫面問清楚。盤點表每一點寫「原本長怎樣 → 改完長怎樣」，改完跟原本差很多（版面、步驟、張數不同）就停下來確認（L-132）。換 logo／換圖：每張原圖先列「構成清單」（有哪些元件、順序、位置），新圖照各自的清單組，不要整批套同一款（L-132 又一次）。
- [ ] 需求文件會被需求方更新：每輪交付前、每次使用者回饋後重抓需求文件跟上次存檔比差異，有新的修改點先列出來（L-136）。
- [ ] 同一個值（價格、折扣、狀態、文案）在列表、內頁、後台、信件、API、報表是否一致。
- [ ] 顯示用的計算與實際執行的計算是否同一套（例：顯示的折後價＝結帳真正折的金額）。
- [ ] 全站共用的元件（頁首、頁尾、浮動按鈕、共用表單）改一處會影響哪些頁。
- [ ] 需求寫「所有頁面都要有／都要跳」：先列出**所有**版型檔（tiles／layout／template 定義、各自載 JS 的獨立頁），逐一標「有載入／沒載入／刻意排除」，排除清單給需求方確認；部署驗證每種版型各抽一頁看有沒有載入（舊站常有兩三套版型，只改其中一套會漏一大片頁面）。
- [ ] 規格寫「A 或 B 不符就擋」：程式要兩個都比（不是 A 有值就不看 B），測試各做「只有 A 錯」「只有 B 錯」「兩個都錯」加「兩個都對」對照組（2026-11-04：年度防呆只看檔名，標題寫去年照樣寫入，QA 才抓到）。
- [ ] 後端修正：同一個查詢條件或輸入防護（WHERE 條件、空白／空字串判斷、狀態與期限檢查）在幾個方法、端點出現？修一處就搜出全部，每處套同一個做法；防護優先寫進條件本身（例：SQL 排除空字串），不要只擋在其中一個方法的入口（2026-10-28：空白判斷只加在一個查詢方法，另一個端點仍會比對到空值資料，QA 才抓到，L-001）。**搜的範圍包含前端 JS 與樣板**裡自己寫的同類判斷（例：`/^https?:\/\//` 預覽），最好改成由伺服器算好、前端只顯示（2026-11-04：網址規則後端改了兩處，表單預覽的 JS 還有一份，QA 才抓到）。
- [ ] 提案書、規格書：同一功能出現在多張表（流程表、功能範圍、時程、串接、指標）時，每張表都要有「階段」欄且彼此一致；目標與效益不寫未量測的數字（改寫「試辦期量測後訂定」）；送審前請審查子代理專門交叉比對一次。

## 3. 資料
- [ ] 既有資料：舊格式、空值、空字串 vs NULL、歷史自由輸入值（例：選單只有 1～8，舊資料是「第一組A」）、半套資料。
- [ ] **用舊資料欄位當顯示或判斷條件**（`startsWith`、`equals`、`isEmpty`、`LIKE 'x%'`）：寫條件前先跑一次值的分布，附在規格——開頭字元的 `hex`（前置空白、全形空白）、大小寫、空字串／NULL／只有空白／HTML 實體（`&nbsp;`）、不符合格式的值（文字、本機檔案路徑）各幾筆、近年各幾筆；判斷前一律先去前後空白；寫入端同時擋掉不合格的值（L-130：近一半網址前面多一個空白，換版頁面判斷成「沒有網址」整個藏起來，三週後才查到）。
- [ ] 需要資料搬移嗎？能重跑嗎？會鎖表多久？換版前跑還是換版後跑（或兩次）？備份與還原怎麼做？
- [ ] 新舊系統並行期間兩邊都會配號的（流水號、附件檔名）：最後同步連**檔案**一起比，同名但內容雜湊不同就是撞號；已知撞號在換版前先處理，不排進長批次（L-198）
- [ ] **改一張表的意思**（加一種新列、改欄位用法）：先搜整個工作區（所有 repo、排程、其他網站）**誰還直接讀這張表**、怎麼讀（有沒有看新欄位、是不是只取第一筆）；改不了的舊程式要讓新資料對它們看不見，並在正式站 SQL 加「舊查法看到的列數不變」的防呆（L-159）。
- [ ] **匯入新一年／一批資料、修資料之前**：跑 `scripts/find_table_readers.py <工作區> <要寫的表>`，把每個讀取處（含同網站的別頁、後台、排程）列進計畫，逐一判斷新資料進來後那頁會顯示什麼（L-159 第二次：只想到本頁，使用者提醒「另一頁也會顯示這份資料」才查，那頁的讀法早就錯了一整年）。跑會寫表的 .sql 而沒查過時，`tool_hints` hook 會提醒。
- [ ] **跨年度／跨批次找「同一個東西」用的鍵每年穩定嗎**：外部代碼（分類代碼、商品編號）常每年重編，找前幾年要用自己的穩定識別碼；同時搜程式裡「今年代碼 + 年份 - 1」這種寫法（L-177）。
- [ ] **衍生／對照表**（從主表算出來存的 rel、快取、彙總表）：主表改鍵、修連結之後有沒有跟著重建；寫入新一年時有沒有一起建（L-178）。
- [ ] 樣板、程式裡**寫死的年份**（`!= 2025`、`'2026'`）：換年度前搜一次，改成看資料（例：有沒有結果資料）而不是看年份（L-179）。
- [ ] **清重複資料（同一個鍵有好幾列）**：① 先找「同一分鐘建立很多列」的批次，對 access log 找出是哪個網址／排程觸發的，分清楚有幾個來源（L-197：一個是後台隱藏功能整批重建、另一個是排程每晚被呼叫兩次）；② 第一輪盤點就**逐欄比對每一欄**（只輸出「相同／不同」的計數，不印姓名、email 的值），把所有不同的欄位一次列給使用者決定留哪邊——不要只比權限相關欄位，被刪那列可能有比較新的來源資料（人事欄位、外部同步值）；③ 查修改紀錄表，看有沒有人在重複出現之後改過「新」那列，改過的照「有異動的優先」處理；④ 刪除放在交易裡、先試跑退回，自動核對「每個鍵剩一列、帳號數不變、特殊權限／設定的數量不變」。
- [ ] 表單沒有帶的欄位，存檔時會不會被清空。
- [ ] 刪除／停用是軟刪除還是硬刪除；唯一索引與軟刪除的交互。
- [ ] 代碼欄位顯示時有沒有轉成中文名稱；**員編、地區代碼、課程代碼給人看時一律「名稱（代碼）」**（2026-10-29：某個人員紀錄只有員編被說不直觀，L-006）。**原因／備註／異動紀錄這類文字欄也算**：逐一盤點寫入點有沒有寫英文代碼，或把代碼變數（外部回覆碼、enum `name()`、狀態值）拼進中文句子——後者掃字串常數抓不到，要看拼接的變數；正式機已有的舊值在顯示層對照，不改資料（例：顯示層對照表＋掃寫入點的測試，本地細節有範例）。**舊值要連歷史版本一起撈**：`git log -p -S` 找每一版寫過的字串，對照正式機部署過哪些版本——只看現行程式會漏掉中間版本寫過的（2026-10-29：中間三個版本寫過一句夾英文內部狀態值的補正說明，QA 才抓到；原句見本地細節）。

## 4. 失敗、重試、併發
- [ ] 外部系統沒回應／逾時／明確拒絕，分別怎麼處理；「查詢失敗」不等於「查無資料」。
- [ ] 出錯後回去的頁面本身不能又呼叫剛失敗的外部服務（例：預覽失敗回上傳頁，上傳頁又打同一支 API，錯誤訊息永遠出不來）；本機實際停掉那個服務各走一次「預覽時斷線」「寫入時斷線→恢復→再按」（2026-11-04 這樣才抓到）。
- [ ] 匯入預覽至少走四種情境：全部正常、整種 0 筆、部分檔案被擋、全部已存在（重傳）。
- [ ] 匯入時「這一列要寫到哪裡」用的鍵，在對位範圍裡唯一嗎？（例：同一筆資料裡用項目組合找第幾層，同科目出現兩層就會寫到同一格、後一列蓋掉前一列。L-158）不唯一要加第二個鍵或照順序指派，並測「同鍵兩列」；已匯入的資料用腳本掃「同鍵多筆、後面全是空值」。
- [ ] 重試會不會無限重送注定失敗的資料；停止重試後怎麼恢復。
- [ ] 兩邊同時寫同一筆（使用者存檔 vs 排程、兩個分頁、重複點擊）會不會重複建立或互相覆蓋。
- [ ] 部分成功（主檔寫入、明細失敗）會留下什麼狀態。
- [ ] 使用者送出的表單：列出**每一條「沒寫入」的路徑**（前端驗證、後端驗證、防灌水／頻率限制、DB 長度與格式限制、例外處理器、回 2xx 但其實沒存）→ 使用者各看到什麼。不准有「沒存卻顯示成功」；前端只認明確的成功狀態碼。DB 才擋得到的限制要在寫入前先檢查並回原因（L-118）。
- [ ] 寄信、推播、呼叫外部 API 這類副作用：在交易 commit **之後**才做（不要在 commit 前），失敗只記 log、不讓已成功的寫入變成錯誤回應；寫檔的副作用在 rollback 時清掉（L-119）。
- [ ] 新增狀態值、付款方式或旗標時：逐支列出會掃這張表的排程與自動入口（送外部系統、改付款狀態、逾時取消、重試），寫明會不會碰到；不該碰的寫成有對照組的測試（本地細節有範例）。
- [ ] 使用者對外部系統有「絕對不能改／不能刪」這類鐵則時：①盤點我方所有呼叫（路徑＋方法），分出唯讀與寫入，寫入的再到對方程式確認只新增、不碰既有資料 ②對方有、但我方不該用的修改端點列出來 ③寫成**允許清單測試**：呼叫的路徑要在清單裡、禁 PUT／PATCH／DELETE、禁止繞過封裝層直接呼叫，附對照組（塞一條沒列的路徑要失敗）④建議對方 API 也對我方帳號擋掉修改端點（雙保險，交使用者決定）。

## 5. 環境
- [ ] 測試環境與正式環境的設定、外部服務版本是否一致；**用正式環境的實際證據判斷**（log、資料），不要從程式碼推論。
- [ ] 正式設定（金鑰、連線字串）不能被開發設定蓋掉。
- [ ] 子路徑部署、時區、快取、反向代理。
- [ ] **系統依賴盤點**（「哪些系統用到 X」、畫架構圖、影響範圍）（L-065）：
  - 每個 repo 搜 **origin 預設分支**（`git grep <詞> $(git symbolic-ref --short refs/remotes/origin/HEAD)`），不搜工作目錄或目前簽出的分支；分支才有的另標「只在分支」。
  - 「A 呼叫的是 B 這支程式」要比**端點路徑**：呼叫端打的路徑對到伺服器端的路由宣告。只靠網址、名稱、IP 判斷的，標「推斷」。
  - 標「正式在用」要附實測紀錄的行號與日期，而且日期晚於最近一次換版或換機；文件只寫「在用」不算實測。
  - 關鍵字除了網址、資料表，也要搜內部 client jar 的套件名與類別名（用 jar 呼叫的專案不會出現網址）。

## 6. 畫面與體驗（UI/UX）
- [ ] 手機（375／320 寬）、平板、桌機（1024／1440）；橫向。
- [ ] 改到「一排項目」（選單、頁籤、按鈕列、麵包屑）：跑 `scripts/check_text_overflow.py <網址> "<項目選擇器>" [--before 展開選單的 JS]`，七種寬度都 PASS 才交付；截圖看到壓字、重疊不能用「參考對象也一樣」放過（L-215）。
- [ ] 手機寬實測 `document.documentElement.scrollWidth` 不大於視窗寬（表格、長字串、複製按鈕最容易撐寬），並截圖看文字有沒有壓到按鈕；**版型修完交 QA 前自己先量一次**。
  `scrollWidth` 合格不代表看得到：`.table-responsive` 裡的表格會自己橫捲，整頁量不出來——每個 `td` 的 `getBoundingClientRect().right` 也要 ≤ 視窗寬，表格手機版改卡片（2026-10-29：異動紀錄原因欄在 390 寬完全看不到，UI/UX 抓到）。
- [ ] 手機驗收前先確認頁面有 `<meta name="viewport">`：沒有的話實機會以桌面版（約 980px）縮小顯示，手機樣式全部不會出現，報告要寫明（2026-10-29 某後台就沒有，模擬器量不出來）。
  量測一定開手機模式（Playwright `is_mobile=True`／DevTools 裝置模擬）：桌機模式的 Chromium 不看 viewport，量到的永遠「正常」；先跑「拿掉 viewport 要量到 980」的對照組（2026-10-30）。
- [ ] 手機上每個可點元素 ≥ 44px（量測腳本直接列出 < 44 的數量，不靠目測）；按鈕組換行後還是一組（例：分頁「最末頁」不能單獨掉到下一行）。卡片、徽章這類標記欄位，原型就要塞「最長的真實組合」（例：已退回＋原因＋無法收款＋原因），不只長名稱（2026-10-30 UI/UX）。
- [ ] 手機模式下內容比螢幕寬時，瀏覽器會把版面視窗撐大（768 變 877），`scrollWidth` 跟著相等：**`innerWidth` 不等於設定寬也算撐破**。用「省略號截斷」的欄（`max-width:0`＋百分比寬）在窄表格會被壓到只剩兩個字，要量被截斷欄的實際寬度，不能只看有沒有橫捲（2026-10-30，QA 抓到）。
- [ ] 平板（768）不能只看「整頁沒撐破」：表格裡重要欄位離畫面超過一個螢幕寬（要捲 600px 以上）就列成待決，不當成通過（2026-10-30）。
- [ ] 桌機回歸不要用截圖像素比對（同一頁拍兩次就有三成多的頁不同）：比元素位置（同一份 HTML 套改前／改後 CSS），改前再載一次當雜訊基準，並用「手機寬一定有差」當對照組。做好的比對工具放 `<本地>/scripts/`（位置記在本地規則）。
- [ ] CSS 用 `var(--x, 預設值)` 時，深色、淺色兩套主題都要定義 `--x`（只靠預設值，深色會出現白字配淺底，2026-11-04 收回鈕對比只剩 1.71）；確認類、危險類按鈕兩種模式都量對比。
- [ ] Bootstrap 預設的欄位錯誤字（`invalid-feedback` 80%）、`code`（粉紅，對比約 3.8:1）低於後台字級與對比規範：用到時要覆蓋（2026-10-29）。
- [ ] 短標籤、姓名、單號、一句話的說明在 375／360 寬量行數（`高度 ÷ line-height`）：該一行的不能折行；放不下時整串換行，不從中間斷字。
- [ ] 圖片載不到（本機常沒有上傳的圖）時，圖上的連結／功能不能跟著整塊消失：留可點的替代（圖示＋文字）。QR code 一定要能點（手機使用者沒辦法掃自己的螢幕）。
- [ ] **後台「預覽」**：直接呼叫前台同一支畫面程式（例：前台 JS 開一個 `open(data)` 給預覽頁用），不要在後台另外手寫一份——兩份一定會長得不一樣（標題被截、字級不同）。交付前把預覽和前台並排截圖比對。全站 css 若有 `!important` 覆寫同一個元件，元件自己的樣式也要處理到。

## 8. 安全與個資
- [ ] 權限檢查在伺服器端，不只靠畫面隱藏（例：唯讀資料直接打 API 也要擋）。
- [ ] 個資遮蔽（身分證中間遮蔽）、API 不回傳不必要的內部欄位。
- [ ] 測試不會打到真實的外部系統（名單系統、金流、正式 ERP、寄信）。
- [ ] **會執行使用者上傳內容的功能**（上傳 HTML 套殼成 JSP／模板、上傳 zip 解到網站目錄；L-219～L-221）：
  1. 檢查**實際要寫出的最終內容**（解析、套殼之後），只扣掉系統自己產生的那幾段原文，其餘不得有任何伺服器端語法；不要只掃上傳的原始內容。
  2. 列出執行引擎**所有**會把檔案當程式的方式（JSP：`<% %>`、`<jsp:`、XML 語法的 JSP、EL `${}`／`#{}`、include、標籤庫），每一種都要有測試；系統的指令放在檔案最前面。
  3. 防護分層後，每一層單獨關掉各驗一次，證明各自擋得住；對照組（全部關掉）要真的被執行，證明測試有效。
  4. 改到「整個路徑」層級的設定（容器 url-pattern、代理、過濾器）時，同路徑沒被針對的檔（圖片、css、js、資料夾網址、既有頁面）逐一比位元組與 Content-Type。
  5. 測試素材用**真實大小**的現有資料，並把現有資料**全部原樣重放**一次，列成功／失敗與原因。
  6. 資源夾（js／css／images）裡的可執行副檔名一律拒絕；資料夾名稱用白名單格式（不能是 `.`、共用資料夾名）；解壓總大小、項目數、單檔大小都有上限，被略過的項目也算進上限。
- [ ] **交付前程式碼自查**（L-111）：
  - 後台頁、匯出、寫入 API、排程管理 API 都有統一的登入／權限攔截（interceptor／guard），不是每支各自判斷，也沒有任何一支漏掉。
  - 沒登入時不會代入預設身分（寫死的會員編號或測試帳號），而是直接擋下。
  - log 和 console 不印密碼、token、cookie、身分證、手機；不用 `toString()` 把整個 DTO 印出來。**登入紀錄、操作紀錄、歷史表也算**：寫進資料表的紀錄物件不帶密碼，寫一支測試抓「寫進紀錄的物件密碼是空的」＋DAO 的 SQL 不含密碼欄。
  - 登入頁、表單樣板的密碼欄不能預填值（`type="password"` 帶 `value`），帳號欄也不留真的帳號。
  - 第三方登入（Google／臉書）、金流回呼一律在伺服器端驗對方的憑證或簽章，不能只收前端送的編號或回應碼；「未綁定」存 NULL，遇到空值、0 一律拒絕（L-246）。
  - 自訂過濾器／攔截器的網址樣式從 context-path 之後寫，並實測一支該擋的網址確實被擋；用腳本列出全部網址與有無登入檢查（L-246）。
  - 管理／監控端點對外要擋：Druid 監控頁（starter ≤ 1.1.9 預設開，L-203）、actuator、swagger、h2-console；交付前從外面打一次只看狀態碼，要 401／404。
  - 金鑰、密碼、私鑰不寫死，也不放在會進版控的設定檔；沒設定時就不讓程式啟動，不用預設值頂替。
  - repo 裡沒有資料庫匯出檔（`.sql` dump）、`.env`、私鑰檔。
  - SQL 不用字串串接請求參數，`ORDER BY` 欄位用白名單。
  - 使用者輸入不用 `v-html`／`innerHTML`／`th:utext` 直接輸出。
  - 驗證用的檢查碼一定要有密鑰，不能只拿公開欄位去做 hash。
  - 前端拿不到不該看的資料，例如正確答案、別人的資料。
  - 依賴注入確實成功（Spring 的欄位有沒有 `final`），`@Transactional` 不要加在 private 方法上，路由對得上前端呼叫。
  - 寫死的測試日期、會員編號、商品代碼都清乾淨。
  - 同一段頁面或邏輯不要複製三份以上，要抽成共用的。
  - 會讀請求參數的過濾器、攔截器：讀之前先設成網站的編碼（或排在編碼過濾器之後）；驗收從伺服器送一筆**不帶 charset 的中文 POST**，看回顯是正常中文（L-165）。
  - 每個對外連線（HTTP 呼叫、資料庫連線池、另一台資料庫）都有連線與讀取逾時（秒級）、連線池等待時間幾秒；首頁這類共用頁面上的非核心區塊，外部失敗時只記 log、那一塊不顯示，不讓整頁 500（L-163）。

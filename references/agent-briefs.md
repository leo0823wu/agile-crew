# 子代理任務簡報範本

子代理看不到你的對話，簡報要**自給自足**：背景、目標、範圍、限制、回報格式都寫進去。
同一階段彼此獨立的角色（例：PM 規格＋UI/UX 方案）放在同一則訊息平行開。
子代理回報後，用 SendMessage 繼續同一個子代理做下一輪（複驗），它會保留上下文。

**先想要不要開**（每開一個子代理，還沒做事就先花約 6 萬 token；量過子代理占總花費三成）：

- 小的需求不開。PM 的工作預設由主對話自己寫（見 `SKILL.md`〈先分級〉）；下面的 PM 範本只在大的需求、而且規格要讀的範圍跟實作要讀的不重疊時用。
- 簡報附上你已經查到的事實與檔案位置，寫明「這些不用再查」，不要讓子代理從頭探索。
- **指定模型**：照步驟做的工作（跑測試、照清單實測、讀頁面、查資料、存檔）用 Agent 工具的 `model` 指定較便宜的模型；要判斷取捨的（規格、設計方案、複查別人的結論）才用跟主對話一樣的。

## 共用：安全限制（每份簡報都要附，依專案調整）

```
## 鐵則
- 只連本機（localhost）；不連正式機、不連正式資料庫。
- 不送出任何會打到真實外部系統的表單或 API（例：名單系統、金流、正式 ERP），自動化測試時在頁面層攔截那些請求。
- 不寄信、不呼叫會寄信的流程（例：註冊）。
- 不 commit、不 push、不部署。審查角色（PM／UI-UX）不改程式碼，只回報建議改法。
- 測試資料用可辨識前綴（例：zzqa-），驗完全部刪除並回報 0 筆殘留；會被瀏覽而累加的計數（點閱數等）先快照、驗完還原。
- 自己開的瀏覽器／程序用完關掉。
- 用中文回報（使用者的語言）。
- 逐項處理的長工作（逐頁、逐檔、逐筆），每做完一項就寫進輸出檔，不要全部做完才一次寫；工作階段中斷時，已做的部分才留得下來。
- 同時有好幾個子代理用同一個工作資料夾時，各自的腳本和暫存檔放在自己的子資料夾（例：`<資料夾>\<批次代號>\`），共用的輸入檔只讀不改；否則同名腳本會互相覆寫。
- 呼叫外部 API／MCP（Notion、專案管理系統（例：OpenProject）等）時，參數裡的中文直接寫；用 Python 產參數一律 `json.dumps(..., ensure_ascii=False)`，不要出現 `\uXXXX`。寫完一定重抓內容，用程式跟預期結果逐字比對。
```

> 為什麼加上面最後一條：定期稽核類工作 2026-10-28 子代理照樣送了 `\uXXXX`，簡報寫「不要」不夠，要直接給做法（`ensure_ascii=False`）。這次沒出錯，是因為寫完有逐字比對。

## 估工時（盲估，評估開發時程合不合理時用）

要判斷「一批功能實際花的工時合不合理」時，讓估算員讀程式碼逐項估，再由主控對照實際工時。五個估算員同時跑時，
下面幾條沒在簡報先定好，每個人做法不同、單項就沒辦法比（第一次試做時五位估算員都回報這幾處不清楚）。

- **盲估**：輸入檔先用腳本去掉實際工時、點數、分數，估算員只拿到功能清單、檔案位置、來源說明；禁止讀評分資料夾其他檔案。實際工時只出現在主控的比對腳本裡。
- **對照組**：同一份簡報另估 1～2 個已知進行順利的專案，比較的是「實際 ÷ 估算」，不是絕對工時（實際工時含開會、等待、部署，本來就大於純開發）。
- **參考錨點**：給一張類型 → 工時範圍的表（靜態頁、複製改欄位、套範本 CRUD、有業務規則、跨系統／排程／併發），偏離要寫理由。
- **先定好歸屬規則**：
  - 共用程式（多個功能共用的 js、DAO）→ 算在第一個用到的功能，備註寫共用給誰。
  - 跨功能的工作（回傳格式統一、資料庫搬移、理解既有系統）→ 一律放 `SETUP`。
  - 做一半的功能 → 照現況估，不補不扣，備註寫缺什麼；交付狀態無法編譯 → 照現況估，另列一條修正。
  - 同一功能有複製也有新寫 → `source` 填工作量較大的那個，備註寫比例。
  - 用 AI 輔助寫的 → 照不靠 AI 的人工工時估。
- **判斷是不是複製要跨 repo 比對**（同一個團隊的其他 repo、舊系統），只看同 repo 會漏；改了參數格式的搬移，逐行相同比例會很低，要對照方法名稱與流程。
- **輸出**：每估完一項就追加一行 jsonl（`id`、`source`、`drivers`、`low`／`likely`／`high`），補品質另列不加進合計。
- **限制要寫**：估算看不到除錯、等規格、外部連不通的時間；low／high 範圍約 ±50%，只能說「明顯偏慢／沒有明顯偏慢」，不拿小差距排名次。

## 複驗（上一輪列的問題修好了沒）

派子代理逐條複驗「已修正」的問題時，結論欄**固定六類**，每類的處置在派工前先定好（沒定就先問使用者），不要讓子代理各自歸類（L-170）：

| 結論 | 意思 | 一般處置 |
|---|---|---|
| 已修好 | 打開目前版本確認問題不在了，附 commit 與檔案:行號 | 解除 |
| 部分修好 | 修了一些，列出還在的檔案:行號 | 視同未修 |
| 未修 | 程式沒動 | 未修 |
| 說不修＋理由 | 負責的人回覆不改並給理由 | 用固定問題判理由：「他說的需求能不能在不留風險下做到？」能＝理由不成立、視同未修；不能（例：要外部系統配合）＝暫不算，但要限期訂出修法 |
| 改法錯誤 | 改了但引入新錯誤 | 原條視同未修，新錯誤另列一條 |
| 有疑義 | 負責的人認為問題不成立 | 看程式事實判；不成立就撤、成立就照算 |

- 以版控現況為準：commit 訊息或回報說改了、檔案卻不在任何分支（`git log --all -S <類別名>`），算未修。
- 回覆欄空白但狀態改成「已修正」的，照樣自己對 commit。
- 「搬位置不等於修好」：金鑰從程式搬進有進版控的設定檔、值沒換，算未修。

# 敏捷做法：待辦排序、分輪交付、完成的定義、進行中上限

這份講的是「一個負責人＋AI 團隊（PM／UI-UX／QA 子代理）」怎麼用敏捷開發的做法。
敏捷的重點不是儀式，是三件事：**小塊交付、早點拿到回饋、每一輪都改進工作方式**。只取對這種工作方式有用的，其餘不搬。

**什麼時候讀**（只讀用到的那一節）：整理待辦時（第 1 節）；中、大的需求開工要切輪次時（第 2 節）；交付前對完成的定義（第 3 節）；
要開新的事、而進行中已經有東西時（第 4 節）；分輪的需求做回顧時（第 5 節）；使用者問「大概要多久」時（第 6 節）。
**小的需求不讀這份**——小的需求就是一輪，完成的定義已經寫在主檔分級表的「驗收」欄。

下面說的**專案紀錄**，是每個專案一份的狀況文件（目前狀況、待辦、工作進度、遇到的問題），放在本地規則 `local-rules.md` 指定的位置；
還沒有的話，先把 `templates/backlog.md` 的〈待辦〉放進專案的 README 或筆記就能開始用。

## 0. 名詞對照

| 敏捷的說法 | 在這個技能裡是什麼 |
|---|---|
| 產品負責人（決定做什麼、先做哪個） | 使用者 |
| 待辦清單（backlog） | 專案紀錄的「待辦」，照第 1 節分段、排序 |
| 使用者故事、驗收條件 | 待辦每項的一句話：為誰｜要達到什麼｜怎樣算完成 |
| 一輪（sprint／迭代） | 一次交付：一個工作階段做得完、驗得了的一塊（第 2 節） |
| 每輪規劃、每輪檢視 | 開工講這一輪做哪幾項、不做哪幾項；交付時展示成果、問下一輪（第 2 節） |
| 完成的定義（Definition of Done） | 第 3 節，照小／中／大 |
| 進行中上限（WIP） | 每個專案進行中最多 2 項（第 4 節） |
| 回顧（retrospective） | 每輪交付後的團隊回顧（`retro.md`），產出是技能改版（第 5 節） |
| 估算 | 小／中／大分級就是估算（第 6 節） |

**不採用的，以及原因**：

- **固定長度的週期**（例：兩週一輪）：AI 團隊一輪是幾小時，瓶頸是負責人看成果、做決定的時間。用「一塊可驗收的成果」當一輪，不用日曆。
- **每日站會**：進度回報固定四件事（做完什麼／正在做什麼／卡在哪／下一步）已經涵蓋。
- **故事點、速度、燃盡圖**：這些是讓多人對齊工作量用的；這裡沒有要對齊的人，回顧已經自動記每輪耗時。
- **圖形看板**：待辦照第 1 節分段之後，文字本身就是看板。負責人自己有看板工具的，寫進本地規則。

## 1. 待辦：排序與拆小

專案紀錄的「待辦」分四段（可複製的格式在 `templates/backlog.md`）：

| 段落 | 放什麼 | 規則 |
|---|---|---|
| **進行中** | 已經動手、還沒交付的 | 最多 2 項（第 4 節）；每項寫做到哪 |
| **接下來** | 下一個要做的 | **有順序**，由上往下做；最多 5 項，多的放「之後」 |
| **之後** | 想做、還沒排的 | 不排序；寫提出日期 |
| **等別人** | 卡在別人回覆或外部條件 | 寫等誰、等什麼、哪一天問的；不占進行中的名額 |

做完的不留在待辦：移到專案紀錄的「工作進度」；紀錄變長時用 `scripts/split_record.py` 把舊的進度搬到歷史檔。

**每項寫一句**：`為誰｜要達到什麼｜怎樣算完成`。
例：`後台人員｜匯入失敗時知道是哪一列、為什麼｜錯誤訊息列出列號與原因，三種常見錯誤各測過一次`。
寫不出「怎樣算完成」的，代表需求還不清楚，先放「之後」並註明要問什麼。

**拆小**：

- 一項要**一輪做得完**（一個工作階段、一次交付）。做不完就拆。
- **照使用者看得到的成果切，不照技術層切**。「先做資料表、再做 API、最後做畫面」切出來的每一塊都驗不了；
  改成「先做能查一筆的最簡單版本（資料表＋API＋畫面都有但很陽春），再加篩選，再加匯出」，每一塊都能給人看、能驗收。
- 拆不出來是因為有不知道的事（外部系統行為、資料長什麼樣）：先排一輪「探路」，產出是答案與建議，不是程式；時間先講定，到了就回報。

**排序依據**（由上往下看，前面的優先）：使用者指定的 → 擋住別項的 → 有期限的 → 最不確定、越早知道越好的 → 其餘照價值。

**誰排**：你提出排序建議與理由，使用者決定。**什麼時候整理**：每次收尾更新專案紀錄時看一次「接下來」的順序還對不對；
新的待辦當下就放進正確的段落，不要全部堆在最後。

## 2. 分輪交付

**什麼時候分輪**：大的需求一律分；中的需求預估一個工作階段做不完時分。小的需求、一般的中的需求就是一輪，不用切。

**一輪多大**：一個工作階段做得完，結束時交出一塊**驗收過、看得到**的成果。寧可小，不要大。

**第一輪做什麼**：最不確定的、或最有價值的那一塊。常見做法是先把整條流程用最陽春的方式打通（每一段都有、但都很簡單），
之後每輪把其中一段做完整。這樣第一輪結束就知道整體行不行。

**開工講清楚（每輪規劃）**，放在第一則回覆：

1. 這一輪的目標，一句話。
2. 做哪幾項（各自的「怎樣算完成」）。
3. **不做哪幾項**（留到後面哪一輪）。
4. 整個需求預計分幾輪、這是第幾輪。

**中途有人加東西**：很小、不影響這一輪目標的，做掉並在回報裡講一句；其餘放進待辦「接下來」，這一輪不做——
使用者堅持要現在做，就請他決定換掉這一輪的哪一項。不要默默把範圍變大。

**每輪交付（每輪檢視）**：

1. 拿實際的成果給使用者看（截圖、可以操作的網址、跑出來的檔案），不是只講做了什麼。
2. 對照開工講的項目逐條寫「做了／沒做（原因）」。
3. 問下一輪：照原本的順序繼續、調整順序或內容、或停在這裡。附你的建議。
   看到成果後改方向是正常的，這就是分輪的目的；改了就更新待辦的順序。

**每一輪都要達到完成的定義**（第 3 節）。不留「之後再一起測」「最後再補文件」——那樣到最後一輪才發現問題，等於沒有分輪。

## 3. 完成的定義

交付前照級別對一次。**沒達到的不能說完成**：交付報告寫「完成 N 項；未完成：…（原因）」，未完成的放回待辦。

**小**

1. 實測過：真實畫面或測試，看的是實際結果。
2. 同一條規則在別處的出現找過一次，要改的都改了。
3. 過了 `edge-case-checklist.md` §8 自查；有畫面的照 UI/UX 技能的交付前檢查走過。
4. 交付報告講清楚有沒有 commit、上線了沒、還差什麼。
5. 專案紀錄更新（目前狀況、待辦）、回顧加一列。

**中**（小的全部，再加）

6. 驗收條件逐條有 QA 子代理的通過結論；修過的地方再驗過。
7. 有畫面變動的，UI/UX 驗過（手機與桌機）。
8. 補了自動化測試，而且證明過測試會紅。
9. 測試資料清乾淨；不相干的改動沒有混在同一個 commit。
10. 使用者看得到的新文案都列出來請他確認了。

**大**（中的全部，再加）

11. QA 至少兩輪。
12. 上線順序與回退方式寫明；這一輪要上線的，上線後看過線上的實際狀態。
13. 文件、踩坑、專案知識檔補了。
14. 要使用者決定的事都有答案，或明確放進待辦「等別人」。

專案有自己的要求（例：一定要過某個掃描、一定要某個人看過）就寫在本地規則，加在這份後面一起對。

## 4. 進行中上限

**每個專案的「進行中」最多 2 項**（本地規則可以改成別的數字）。

- 為什麼：做到一半的事，每次回來都要重新讀、重新想；同時開的事越多，每一件都越慢，也越容易漏。先做完一件再開下一件，整體比較快。
- **等別人回覆的不算進行中**：移到「等別人」，寫等誰、等什麼、哪一天問的。回覆來了再移回「接下來」的最上面。
- **已經滿了還要開新的**：先把一項收尾；或跟使用者講「現在進行中有 A、B，要開 C 的話建議先暫停哪一項」，
  暫停的移回「接下來」並寫做到哪。緊急的事可以插隊，但同樣要講明暫停了哪一項。
- **開工發現已經超過上限**：第一則回覆講一句，並建議先收哪一項。
- 「等別人」超過一週沒動的，收尾時提醒使用者一次：要追、要改做法、還是放掉。

## 5. 回顧接上輪次

- 每輪交付後照 `retro.md` 做回顧，做法不變。
- 分輪的需求，回顧那一列的「指標摘要」多寫 `範圍 做完/講好`（例：`範圍 3/4`），沒做完的寫原因。
- **連續兩輪沒做完講好的範圍**：下一輪把範圍切小，不是加快速度。
- 多輪需求的最後一輪，回顧多答一題：**切法對不對**——哪一輪切太大、順序該不該換、哪一塊應該更早給使用者看。
  有發現就改這份的第 1、2 節，照 `retro.md` 第 3 步記進改版紀錄。

## 6. 估算

- **分級就是估算**：小／中／大決定了出動多少人、驗收幾輪、要不要分輪。不另外估點數或工時。
- 使用者問「大概要多久」：看回顧紀錄裡同級別最近幾輪的耗時（`scripts/team_metrics.py --trend`），回答一個範圍，並講明這是過去的數字。
- 分級估錯（做到一半發現比想的大）：當下升級並講一句，照新的級別補做該做的事（主檔〈先分級〉）。

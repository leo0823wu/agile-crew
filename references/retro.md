# 團隊回顧（每次交付後必做）

`lessons-*.md` 記的是「踩到的坑」（被糾正、出錯）；這份講的是**團隊怎麼工作**：哪裡慢、哪裡重工、哪裡品質沒顧到、
下次流程要怎麼改。目的：每做一次，下一次更順、品質更好、速度更快。

**回顧的產出是「技能改版」，不是報告**。指標和四個問題只是用來找出要改哪裡；真正算數的是第 3 步改了什麼，
以及之後在改版紀錄裡驗證那個改動有沒有效。

> **本檔是可分享的流程**。每次回顧的紀錄、趨勢、改版紀錄都有專案名稱與使用者原話，一律寫在**本地資料夾**（`<本地>`，見 `shareable.md`）：
> `<本地>/retro-log.md`（〈趨勢〉〈回顧紀錄〉）、`<本地>/skill-changelog.md`（技能改版與成效）。

## 什麼時候做

- 每次**交付給使用者之後**（驗收通過、回報完成），同一個工作階段內做，不要拖到下次。
- 一個需求分好幾輪交付時，每輪各做一次（可以很短）。
- **自動檢查**：Stop hook `hooks/stop_gate.py`（＝`retro_gate.py`＋`record_gate.py`）——工作階段裡最後一次 `git push` 之後沒有改過 `<本地>/retro-log.md`，就擋下結束、要求先做回顧（擋一次，之後放行避免卡死）。真的沒有要改的，也要加一列寫明原因。測試 `hooks/test_retro_gate.py`、`test_record_gate.py`、`test_stop_gate.py`（全部一次跑：`scripts/run_tests.py`）。
  同一個入口也檢查**專案紀錄**：這一輪 push 了或寫了回顧，而這一輪改過的檔（或回顧那一列寫的專案）對到的專案紀錄沒更新，就擋一次並列出要更新哪一份（`record_gate.py` 開頭有完整判斷規則；回放 `hooks/replay_record_gate.py 30`）。所以回顧那一列的「專案／這輪」**開頭寫專案名稱**（例：「官網 正式機上線」，用紀錄資料夾的名稱或它去掉「官網／系統／平台」的簡稱；本地別名設在 `config.json` 的 `record_gate.aliases`），hook 靠它對到紀錄。
  🔴 **回顧紀錄一律用 Edit／Write 工具改**：hook 是看工具呼叫認的，用 Python 腳本改（腳本路徑沒有 `retro-log.md`）它認不出來，會再擋一次。
- **開工自動帶入**：SessionStart hook `hooks/session_brief.py` 把 `retro-log.md` 最近 8 列的 ⏳、改版紀錄裡待驗證的改動、再犯 ≥ 2 還不是機制的 lessons、這個目錄對到的專案 ⏳ 待辦放進對話開頭（只是提醒，跟這次有關的仍要照第 0 步處理）。
- ⏳ 的寫法要讓 hook 抓得到：`⏳ <一句話做什麼>`，多項用「；」分開（hook 抓 ⏳ 後面到「；」為止）。不是待辦的地方不要寫 ⏳ 這個符號。

## 怎麼做（10 分鐘內）

### 0. 先對上一輪的行動項，再查有沒有「規則已經有卻沒照做」

- `retro-log.md` 標 ⏳ 的行動項：這次有沒有落地？沒落地的寫原因，決定繼續、改做法或取消。
- **驗證之前的技能改版有沒有效**：看 `skill-changelog.md` 成效是 ⏳ 的列，這次工作有碰到它要解決的問題的，填 ✅ 有效／❌ 沒效（附日期）。❌ 的這次回顧就換做法，升一級。
- 這次出的每個問題，先到 `lessons-workflow.md`／`lessons-tech.md`／`<本地>/lessons-local.md` 找有沒有寫過：
  - **寫過卻沒照做** → 不新增列，改成「強化」：原列「再犯」欄 +1、補「又一次（日期）」，並往上升一級——
    規則文字 → 寫進子代理簡報範本或清單 → 腳本／測試檢查 → hook。
    **再犯到 2 次還不是機制的，這次就要做成機制**：會擋的放 `hooks/guard_tool_input.py`、只提醒的放 `hooks/tool_hints.py`，
    同時在對應的 `test_*.py` 加「該擋／不該擋」對照，跑過全 PASS 才算。
  - 沒寫過 → 才新增一列，編號用 `scripts/lesson_id.py next` 取。
  - 「主要發現」寫編號（例：「L-042 又犯」），方便之後統計哪幾條最常被違反。
  （參考：Lance Martin〈Claude Diary〉回顧時先找違規；Every compound engineering 新增前先比對重疊。）

### 1. 量指標（照實填，沒有就寫 0）

| 指標 | 意思 |
|---|---|
| 使用者糾正 | 使用者指出「不對／不是這個意思／你漏了」的次數 |
| 使用者追問狀況 | 「現在是什麼狀況」「做好了沒」這類追問次數（代表回報不夠） |
| QA 退回 | QA／UI-UX 驗收不通過、要修再驗的輪數 |
| 重工 | 做了又整個拿掉或重做的部分（寫是什麼、大約花多久） |
| 子代理問題 | 簡報不清楚導致做錯、超出範圍改檔、互相干擾（共用資料、共用帳號、同時跑服務）、回報漏東西 |
| 等待 | 卡在等使用者、等環境、等子代理的時間，以及原因 |
| 漏到最後才發現 | 本來在盤點或規劃階段就該想到、卻在實作或驗收才冒出來的事 |
| 接手問、接手重做 | **只有接手別的工作階段交接的那一輪才填**：回頭問使用者「之前做到哪」這類前一個工作階段已經知道的事幾次；重做前一個已經做過的事（重讀同一批檔、重跑同一個掃描）幾件。在「指標摘要」寫 `接手問 N`、`接手重做 N`，並在「主要發現」寫交接單缺了哪一項（見 `handoff.md` 第 4 節） |
| 範圍 | **只有分輪交付的需求才填**（`agile.md` 第 2、5 節）：開工講好這一輪做 M 項、實際做完 N 項，在「指標摘要」寫 `範圍 N/M`，沒做完的在「主要發現」寫原因。連續兩輪沒做完，下一輪把範圍切小。這一格目前只給人看，腳本不統計 |

「指標摘要」一律寫 `糾正 N`、`追問 N`、`QA 退回 N`、`重工 N`（沒有寫 0；重工的內容寫在括號裡），`scripts/team_metrics.py` 才抓得到。
**耗時不用自己算**：加完那一列跑 `python -I scripts/round_time.py --fill`，會從工作階段紀錄算出「從使用者提出需求到寫回顧」的時間，
以及其中等使用者、等外部（超過 3 分鐘的 ssh、scp、push、curl 這類等網路的指令、等背景工作；建置、測試、本機 sleep 輪詢算工作）各多久，
填進「耗時」欄空著的格子（格式 `開發 3.2h（等使用者 1.0h、等外部 0.2h）`；手寫的不覆蓋；
「問答」＝這一輪沒改檔、沒 git、沒用子代理；「補寫」＝被 hook 擋下才補做的回顧，不算進趨勢）。工作階段紀錄 30 天後會被清掉，所以要當下跑。
改了算法要重算舊列：加 `--recompute`（只重算自動算出的格子）。

### 2. 回答四個問題

1. **哪裡最慢？** 時間花在哪，哪一段其實可以平行、可以提早、可以不做。
2. **哪裡重工？** 根本原因是什麼（需求沒問清楚、規格數字兩處不一致、沒先看現況…）。
3. **品質漏洞**：使用者或 QA 抓到、但我們自己應該先抓到的問題，下次在哪一步擋。
4. **做得好、要保留的**：這次有效的做法（下次照做）。

### 3. 改技能（最重要，回顧的主要產出）

每個發現都要變成**具體改動**，直接改檔，不是只寫「下次注意」。每改一處就在 `<本地>/skill-changelog.md` 最上面加一列，寫清楚要解決的問題和**之後看什麼訊號判斷有效**。
只在 lessons 加一列文字不算改技能；同一個問題已經記過文字，這次就要往上升一級（範本／清單 → 腳本／測試 → hook）。
改 hook 或腳本：先寫「該擋／不該擋」測試、用歷史指令回放（`hooks/replay_guard.py`）確認不會大量誤擋，全 PASS 才掛上；有疑慮（可能擋到正常工作）先問使用者。

**先分層再寫**（規則見 `shareable.md`）：通用的流程面、技術面改進寫進技能；跟這個人、這家公司、這個專案有關的寫進本地。

| 發現的類型 | 通用的寫進技能 | 個人／公司／專案的寫進本地 |
|---|---|---|
| 子代理簡報不清楚、範圍沒講、互相干擾 | `agent-briefs.md` 的範本 | `<本地>/local-rules.md`（例：公司的測試帳號規則） |
| 盤點漏掉某類情況 | `edge-case-checklist.md` 加一項 | `<本地>/local-rules.md` |
| 流程順序、交付格式要改 | `SKILL.md` 對應步驟（只加一行規則＋編號；經過與細節寫進踩坑表那一列） |
| 某個動作一做就會踩的坑（跑某種指令、某種腳本） | `hooks/tool_hints.py` 加動作當下的提醒＋`test_tool_hints.py` 測試，改前用過去的指令回放看誤報 | — | `<本地>/local-rules.md`（例：紀錄放哪、部署慣例） |
| 踩坑 | `lessons-workflow.md`／`lessons-tech.md` 最接近的段落 | `<本地>/lessons-local.md`（整列只適用本地，或通用列的本地細節） |
| 只跟某個專案有關 | — | 該專案的 `CLAUDE.md`／檢討文件／記憶 |
| 重複做的手動步驟 | 通用的寫成 `scripts/` 工具 | 只適用某專案的放 `<本地>/scripts/` |

沒有任何要改的，也要寫一句「這次沒有要改的，因為…」。

每個行動項寫成（參考 Google SRE 事後檢討的行動項格式）：**類型**（預防／提早發現／減輕影響）｜**改哪個檔或腳本**｜**怎麼驗證有效**｜**狀態**（✅ 已改／⏳ 待做）。
改得到的當場改完標 ✅；要使用者同意或要等時機的標 ⏳，下次開工第 0 步會被追。

**寫進技能之後**跑 `python -I scripts/check_shareable.py`，要 0 行（技能裡不能有個人或公司資料；字清單在 `<本地>/private-terms.txt`，碰到新的公司用語、專案名、人名就加進去）。

### 定期技能優化（手動跑）

跨好幾次回顧才看得出來的問題（同一類問題在不同專案重複、某個範本一直被繞過、某個改動一直沒效），定期整理一次：
`scripts/team_metrics.py` 算數字與改版成效（`--trend` 只看每週趨勢：糾正、追問、QA 退回、重工、耗時，分開發任務／小問答）→ 找出跨回顧的共同模式 → **直接改技能**（同第 3 步，記進改版紀錄）→ 順手合併重複的 lessons、把過時的移到〈舊做法〉、修重號 → 在 `retro-log.md`〈趨勢〉加一列。
改檔前先備份；紀錄以「改了哪些技能、為什麼、怎麼驗證」為主。數字沒變好的項目，回頭查是改動沒做完、沒效，還是根因找錯了。

### 4. 記錄與回報

- 在 `<本地>/retro-log.md`〈回顧紀錄〉最上面加一列（「耗時」欄留空），接著跑 `python -I scripts/round_time.py --fill` 填耗時。
- 專案的檢討文件或專案紀錄照本地規則寫（詳細 Q&A 在那裡，回顧紀錄只放一列摘要）。
- 「已改（檔案）」欄寫技能改了哪幾個檔；改版的細節（問題、預期訊號）寫在 `skill-changelog.md`。
- 交付報告最後加 2～3 行：「技能改了什麼（哪幾個檔）、之前的哪個改動這次證實有效／沒效」。不要把回顧內容整段搬給使用者。
